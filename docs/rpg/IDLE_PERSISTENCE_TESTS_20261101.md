# 공통 SQLite와 방치 성장 저장 검증 (2026-11-01)

`scripts/rpg/test-idle-persistence.ts`는 임시 파일에 연결한 실제 SQLite 연결 두 개와 실제 `RogueService(..., idleMode=true)`를 사용한다. 테스트 더블이 성공했다고 가정하는 대신 두 번째 연결에서 커밋 전/후 데이터를 읽고, SQL 트리거 및 COMMIT 직전 예외를 주입해 저장 상태를 검사한다.

## 검사하는 불변 조건

- 기존 `players.sqlite`와 `items.sqlite`의 플레이어, 골드, 영혼석, 원래 링크, 주얼, 보관함 링크, 지급 사건과 구매 영수증을 공통 `game.sqlite`로 보존한다. 재개방은 중복 이전/지급을 하지 않는다.
- 홀덤 재화 차감과 주얼 지급은 같은 SQLite 연결의 한 트랜잭션이다. 다른 연결은 둘 다 커밋된 뒤에만 본다. 주얼 지급 다음의 지갑 UPDATE가 실패해도 주얼, 영수증, 아이템 revision과 지갑 차감이 모두 취소된다.
- 중첩된 플레이어 저장, 주얼 지급, 우승 보상 후 실패하면 모든 쓰기가 함께 취소된다.
- 핸드 결과의 모든 사람 지갑과 정산 ID는 함께 저장한다. 정산 ID 재전송은 스택을 다시 쓰지 않는다. 새 지갑 런타임은 테이블에 맡긴 마지막 커밋 금액을 돌려주며, 이전 런타임 epoch의 쓰기를 거부한다.
- 커밋에 실패한 스택이 이후 disconnect 같은 이름/접속 정보 저장을 통해 되살아나지 않는다. 퇴장 저장 실패 후 재시도는 예치금을 한 번만 돌려준다.
- 실제 장비는 낮은 레벨 아이템으로 교체할 수 있다. 이전 무기 종류별 강화 기록을 보존하면서 새 장착 아이템 레벨로 재개방할 수 있다.
- 이전 v2 링크와 선택 액티브는 보관하고, 필요한 보유 젬 복사본은 수량대로 한 번 부여한다. 전투에는 실제 장비 소켓만 영향을 준다. 장착하지 않은 인벤토리 아이템의 소켓도 보유 복사본을 사용한다.
- 서버 wall clock의 같은 구간은 재시도·재입장·두 서비스 연결에서 한 번만 누적된다. 역행하는 시계는 이전 누적 시각을 뒤로 돌리지 않는다.
- 소환의 재화 차감과 결과는 같은 플레이어 revision에 기록된다. 저장 실패 또는 응답 스냅샷 생성 실패는 DB를 롤백하고 변경된 런타임 세션을 버린다.
- 방치 tick의 저장 실패 뒤 재입장하면 누락된 구간을 한 번 누적한다. 유효하지 않은 순수 명령은 시계나 sequence를 소비하지 않으며, 순서가 틀린 요청 뒤 올바른 다음 요청은 계속 사용할 수 있다.
- 첫 입장 COMMIT 실패는 저장되지 않은 시작 보너스나 임시 세션을 게시하지 않는다. 이전 세션 ID로 보낸 요청이 새 유효 세션을 제거하지 않는다.
- 캠페인도 같은 트랜잭션 경계를 사용한다. 50ms tick마다 무기 구성을 재설정해 진행 중 타격을 취소하지 않으며, 실제 시전이 피해를 가하는 것을 확인한다.
- 실제 보스 생존→사망 전이는 서버의 진행 단계별로 초월석을 한 번 지급한다. 무작위 맵 seed나 골드 증분으로 지급 키를 만들지 않는다. 보스 보상 SQL 실패는 같은 tick의 처치 보상과 함께 롤백되고 실행 중 세션은 버린다.

## 실패 주입으로 찾은 수정 대상

검토에서는 저장 전 방치 시계를 런타임에 먼저 반영하는 문제, 낮은 레벨 물리 무기 장착 후 이전 강화 기록과의 검증 충돌, COMMIT 실패 후 캐시된 핸드 스택이 다시 저장되는 문제, 퇴장 실패 후 좌석 예약이 사라지는 문제, 첫 입장 실패의 캐시, 성공한 이전 요청의 dirty 상태가 순서 오류에 전파되는 문제, 캠페인 tick의 불필요한 무기 재설정으로 타격이 매번 취소되는 문제를 재현했다. 회귀 검사는 이런 실패를 성공 기대값으로 덮어쓰지 않고, 수정 뒤에도 동일한 주입 지점을 유지한다.

## 검증 경계

이 검사는 동기 SQLite 트랜잭션, 재시도, 두 연결의 가시성, 재개방과 런타임 epoch의 실제 구현을 대상으로 한다. 중간 핸드 전체를 저장·재연하는 기능은 아니며 마지막 커밋된 금액을 복원한다. 운영 파일시스템이 유지되는지, 백업 복구가 되는지, 호스팅의 디스크가 영구 볼륨인지까지 단위 테스트가 보장하지 않는다. 파일시스템 소실 뒤 데이터를 복원할 수 있다는 주장이나 모든 오류가 없다는 주장은 하지 않는다.

`AGENTS.md`의 형식 검증 정책을 검토했다. 이 변경의 주요 실패는 실제 SQLite 트랜잭션 경계와 캐시/DB 대응 지점에 직접 예외를 주입해 재현할 수 있다. 기존 회귀와 위 불변 조건 검사를 먼저 적용했으며, 별도 TLA+/Lean/Kani 모델을 만들거나 형식 검증 통과를 주장하지 않는다. 이 판단은 SQLite 자체나 배포 인프라 전체에 대한 증명이 아니다.
