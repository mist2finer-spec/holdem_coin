## 2. 카메라와 화면 배치

**첫 미술 패스에서는 현재 세로 HUD를 기준으로 작업한다.** 영상은 거의 전체가 가로 월드 화면이고 현재 앱은 상단 약 절반이 월드다. 두 화면의 차이를 셰이더로 해결할 수는 없다.

- 캐릭터 크기는 전체 1080×2340 캔버스가 아니라 실제 `camera.pixelRect` 높이에 대한 비율로 측정한다. 사이드뷰는 20~25%, 쿼터뷰는 12~16%를 초기 비교값으로 삼되 휴대폰 판독성에 맞춰 조정한다. 숫자는 레퍼런스의 대략값이며 합격을 강제하는 값이 아니다.
- 현재 Mount side `(pitch10, yaw0, FOV20, distance24, pivot0/2/0)`를 기준으로 거리·FOV·pivot을 한 번에 모두 바꾸지 않는다. 카메라 앞 풀, 길, NPC와의 겹침을 확인하며 캐릭터의 화면 높이부터 조정한다.
- 원근 카메라를 유지하고 긴 초점거리 느낌을 조정한다. 정사영 전환은 별도 시안으로만 비교한다. 정사영에서는 Z축으로 멀리 놓기만 해서는 이동 시차가 생기지 않으므로 레이어 이동 계수가 필요하다.
- `BattleCameraController`와 `ViewPresentationCoordinator`의 공유 전환 진행도를 사용한다. HUD·입력·가림이 서로 다른 타이머로 전환하지 않게 한다.
- 기기의 안전 영역, 터치 가림, 보스 전조 포함 여부를 확인한다. 현재보다 월드 면적이 더 필요하면 **월드 확대 HUD 시안**을 별도로 비교한다. 화면 방향 변경이나 하단 UI 전체 삭제를 미술 작업의 전제로 삼지 않는다.
- 이동 시차가 과하면 근경·중경의 깊이, FOV, 배치를 먼저 조정한다. 과도한 선행 이동이나 추종 지연은 `lookAhead`와 카메라 추종에서 별도로 조정한다. 게임의 6m/s 이동·서버 충돌 크기를 미술 구도에 맞춰 임의 변경하지 않는다.

### 사이드뷰 5층 배치

Z는 카메라 깊이와 현재 좌표계를 확인해 배치한다. 아래 순서는 화면 기능을 뜻하며 고정 월드 Z 숫자가 아니다.

| 층 | 제작·배치 방식 | 보호할 요소 |
| --- | --- | --- |
| 1. 최전경 | 넓고 뾰족한 풀 묶음·드문 흰 꽃. 화면 하단 테두리에 집중, 캐릭터 앞은 낮추거나 옆으로 눕힘. | 주인공 몸통·무기·적·상호작용 프롬프트를 가리지 않음. |
| 2. 플레이 트랙 | 기존 지형·높이 유지. 황토색 길과 불규칙한 짧은 풀 경계. 지면 큰 색 패치와 풀 색을 공유. | 이동 판정·서버 높이·발 접지 보존. 길 중앙 밀도는 거의 0. |
| 3. 상호작용 중경 | 천막 프레임·천·보드·작업대·화로·NPC를 실제 3D로 조립. 같은 소품을 쿼터뷰에서도 재사용. | NPC 주변 빈 공간, 말풍선 위치, 천막 기둥과 플레이 경로 분리. |
| 4. 숲·언덕 | 기존 저해상도 중경 메시 + 단순 수관 군집. 개별 잎보다 덩어리 실루엣. | 시점 전환 가능한 영역은 카드를 옆에서 보지 않도록 메시 사용. |
| 5. 산·하늘 | 기존 cubemap을 대기색·낮은 대비로 재제작. 필요한 일부 산만 저해상도 메시/불투명 배경 카드. | Cubemap은 이동 시차가 없으므로 시차를 줄 대상은 4층에 둠. |

원경의 흐릿함은 먼저 색·대비·텍스처 세부 묘사를 줄여 만든다. 실시간 DOF나 전체 화면 블러를 기본 전제로 하지 않는다. “5층”은 다섯 Unity Scene이나 다섯 카메라를 뜻하지 않는다. 한 구역 환경 루트 안의 배치 그룹이다.

### 쿼터뷰 전투 배치

활성 구역과 카메라에 보이는 경계까지만 상세하게 만든다. 중앙 전투 바닥은 짧은 풀/지면, 바깥은 긴 풀·바위·수관으로 구획한다. 풀을 화면 전체에 동일 밀도로 채우지 않는다. 보스의 바닥 전조는 풀과 아군 이펙트보다 잘 읽히게 하고, 지형은 기존 가림 처리를 유지하고, 나무·기둥은 기존 소품 가림 경로와 해당 재질의 대응 여부를 확인한 뒤 필요한 처리를 추가한다. 지형 디더가 모든 소품에 자동 적용된다고 가정하지 않는다. 가림 처리가 길이나 접지면에 불필요한 구멍을 만들지 않는지도 확인한다.

## 3. 풀: 기존 구현을 다듬는 순서

### 3.1 지면과 군락을 하나의 기준으로 제작

1. 기존 지형 위에 **길 제외 / 짧은 풀 / 긴 풀 군락 / 꽃 / 전투 가독성 영역** 마스크를 제작한다. 원본 지형을 다시 생성하지 않는다.
2. 넓은 연두·중간 녹색·청록색 패치를 먼저 배치한다. 같은 패치 ID나 월드 좌표를 지면색과 잎 뿌리색·밀도·높이에 적용한다. 모든 잎마다 독립 RGB 난수를 주지 않는다.
3. 길의 양쪽 경계를 직선처럼 동일 간격으로 채우지 않는다. 풀 덩어리와 빈 공간을 번갈아 놓고 텐트 입구·NPC·전투 동선에는 배치하지 않는다.
4. 에디터에서 마스크를 결정론적으로 샘플링해 위치·회전·크기 데이터를 굽는다. 매 프레임 수천 번 Raycast하거나 풀 GameObject를 생성하지 않는다.
5. 짧은 풀 2~3형태, 긴 풀 2~3형태, 꽃 1~2형태를 첫 제작 묶음으로 삼는다. 기존 near/far 메시와 같은 렌더 경로를 사용한다. 다양성은 메시 수보다 군락 배치와 제한된 색 변화로 만든다.

이 마스크·군락 규칙은 **새로 추가할 제작 데이터**다. 현재 코드에 이미 해당 시스템이 있다고 가정하지 않는다. 제안 자산 이름은 `ZoneArtProfile` / `GrassDistribution`이며 기존 리소스와 충돌 여부를 먼저 확인한다.

### 3.2 메시·애니메이션

- 풀은 **정적 메시 + 인스턴싱 + 버텍스 바람 + 근거리 굽힘**으로 유지한다. 풀잎마다 본·스킨·Animator·Collider·Rigidbody를 만들지 않는다.
- UV.y=0은 뿌리, UV.y=1은 끝으로 맞춘다. 최소한 중간에 굽힐 수 있는 정점이 있는 넓은 잎 실루엣을 만든다. near는 곡률이 보이는 형태, far는 더 적은 면으로 큰 실루엣만 유지한다.
- 현재 0.11m 바람과 1.1m 플레이어 굽힘을 기준 캡처 후 조정한다. 짧은 풀과 긴 풀의 같은 변위가 부자연스러우면 높이별 가중치를 적용한다. 바람과 접촉을 더해도 뿌리는 움직이지 않게 한다.
- 현 구현은 위치에 즉시 반응하며 시간 이력은 없다. 처음에는 플레이어 주변의 부드러운 영향 함수와 제한된 방향 반응을 보강한다. 지속 흔적이 꼭 필요할 때만 저해상도 상호작용 텍스처 또는 제한된 영향점 버퍼를 검토한다. 두 방식을 동시에 도입하지 않는다.
- 공격 반응은 기존 타격 표현 이벤트에서 짧은 방향성 굽힘으로 전달한다. 권위 전투 판정이나 풀 충돌로 다시 피해를 계산하지 않는다.

### 3.3 밀도를 높이기 전에 확인할 기술 조건

현재 `MapReviewGrass.Rebuild()`는 셀의 행렬 배열을 만들고 `Update()`에서 셀당 한 번 제출한다. 단순히 positions 수를 늘리면 아래 문제가 생길 수 있다.

| 점검 | 조치 |
| --- | --- |
| 한 번의 인스턴스 제출 제한 | Unity 버전·인스턴스 데이터에 맞는 호출당 제한을 확인하고 셀 내부 배열을 안전한 배치로 분할한다. API상 최대 1023이며 기본 양방향 변환 행렬을 사용하면 문서상 511이다. 실제 셰이더·데이터 조건의 제한을 따른다. 큰 배열을 무조건 한 번 제출하지 않는다. |
| 컬링 경계 | 현재 bounds 확장 2m를 새 메시 높이·회전·바람·굽힘의 최대 변위와 대조한다. 화면 가장자리에서 흔들리는 잎이 잘리지 않아야 한다. |
| 거리 기준 | 현 17/32m는 카메라가 아닌 플레이어 중심이다. 사이드·쿼터 구도의 화면 빈 구간과 팝인을 확인한 뒤 필요할 때 화면 크기/시점별 기준을 추가한다. |
| 재질 수 | 색 패치마다 material 복제하지 않는다. 공유 재질과 검증된 인스턴스 속성 또는 월드 좌표 마스크를 사용한다. |
| 활성화·할당 | 현 `Rebuild()`는 배열·사전을 생성한다. 로드·활성화 시 중복 호출과 할당을 측정한 후 불필요한 재생성을 줄인다. 근거 없이 캐시를 추가하지 않는다. |
| 원거리 비용 | 먼 풀은 메시뿐 아니라 밀도·바람 계산을 줄이거나 지면색으로 이어지게 한다. LOD 전환 디더는 오버드로·쉐이더 비용을 측정한 뒤 선택한다. |

인스턴싱은 전체 풀을 무조건 한 draw call로 만든다는 뜻이 아니다. 셀·메시·재질·패스별 제출이 생기며 Unity는 한 제출 묶음을 bounds 기준으로 취급한다. 현재 6m 셀 컬링을 유지한다. 공식 근거: [RenderMeshInstanced][unity-instancing].

현재 불투명 잎 메시를 기본으로 삼는다. 교차 알파 카드는 필요한 꽃·먼 수풀에서 작은 면적부터 비교한다. 카드가 항상 더 빠르다는 보장은 없다. 같은 장면·해상도·GPU에서 오버드로와 프레임 시간을 측정한다. 파티클도 수량뿐 아니라 화면 점유 면적을 제한한다. [Unity 모바일 아트 최적화][unity-mobile].

## 4. Tripo와 자산 제작 명세

Tripo는 **중경 소품의 초안 생성**에 사용한다. 현재 지형, 플레이어와 전투 리깅, 풀 렌더러를 교체하기 위한 도구로 시작하지 않는다. 참조 영상의 제작 도구는 확인되지 않았다.

| 제작 대상 | 생성·분할 단위 | 엔진 반입 규칙 |
| --- | --- | --- |
| 주황/민트 천막 | 기둥 프레임 / 지붕 천 / 드리운 천 / 현수막을 기능별 분리 | 프레임은 정적, 천은 필요할 때만 제한된 흔들림. 작은 장식을 모두 별도 draw로 나누지 말고 최종 조립 후 재질·메시 병합 검토. |
| 작업대·퀘스트 보드 | 테이블 / 보드 / 소품 묶음 | 종이·책의 세부는 텍스처로 단순화. 입력·충돌은 단순 프록시. |
| 화로·대장간 | 본체 / 발광부 / 연기·불 효과 | 본체 메시와 파티클 분리. 실시간 광원은 우선 없이 emissive로 비교. |
| 바위·나무 | 큰 바위 실루엣 / 줄기 / 덩어리 수관 | 원경에는 저해상도 대체. 나뭇잎 한 장씩 생성하지 않음. |
| 풀·꽃 | 전용 저폴리 잎 묶음을 수작업 또는 절차 제작 | 높이 UV, 뿌리 pivot, near/far 메시, 공유 재질. 리깅 없음. |
| NPC | 기존 호환 리그·애니메이션 우선 재사용 | 신규 스킨 모델 필요 시에만 별도 본·스킨 검수. 주인공 원본은 보존. |

각 소품은 다음 묶음으로 인계한다.

- 보관용 원본 생성 파일(`.glb` 등)과 정리한 편집 원본, 반입용 메시(`.fbx` 등 프로젝트가 지원하는 형식).
- BaseColor, 필요한 경우 Normal과 재질 마스크. **광택을 꺼도 BaseColor에 구워진 얼룩·그림자는 사라지지 않으므로** 텍스처의 과한 디테일과 명암을 먼저 정리한다.
- 미터 단위 스케일, 바닥 pivot, 정상 노멀·UV, 의도된 재질 슬롯, LOD, 단순 충돌 프록시, 사용 권한·생성 출처 기록.
- 최초 제작 가이드로 소품당 1~2개 재질을 지향한다. 삼각형·텍스처 제한은 화면 점유율과 실기 측정으로 확정한다. AI 출력 원본의 폴리곤 수를 성능 예산으로 받아들이지 않는다.

파일명 예: `Tent_Frame_A`, `Tent_Cloth_Orange_A`, `Forge_Body_A`, `Grass_Short_A_LOD0/LOD1`. 제안 이름이며 현재 저장소에 존재한다는 의미가 아니다.

## 5. 색·조명·액션

기존 Nilo 캐릭터 표현과 Mount 전용 셰이더의 동작을 유지하며 팔레트를 통일한다. 모든 재질에 똑같은 2단 명암을 강요하지 않는다.

- 지면은 큰 색면, 풀은 뿌리→끝 그라데이션과 군락색, 천막은 부드러운 천 명암, 나무·돌은 약한 디테일, 원경은 밝고 낮은 대비로 분리한다.
- 무기·금속 화로의 제한된 하이라이트는 남긴다. 블룸은 발광부와 타격 순간만 보조하고 화면 전체의 흰 막처럼 사용하지 않는다.
- 최신 `ZoneGround.shader`의 전경 디더는 Forward/DepthOnly에서 일치해야 한다. 셰이더를 바꾸며 깊이 패스나 현재 가림 처리를 누락하지 않는다.
- PoE식 느낌은 어두운 배경색이나 많은 적부터 넣는 방식보다 **공격 준비→타격→회복의 구분, 이동 중 스킬 사용 감각, 적별 전조, 빌드 효과의 차이**로 만든다. 기존 피해·스킬·판정 규칙을 미술과 섞어 임의 변경하지 않는다.
- 기존 `attackId`/strike/contact 시점 및 공유 표현 흐름에 흰 베기 호, 짧은 피격 강조, 피해 숫자를 연결한다. 프레임마다 같은 타격 효과를 중복 생성하지 않는다. 카메라 흔들림·hit-stop은 입력과 서버 시간을 멈추지 않는 표현 범위에서 검증한다.
- 이펙트는 풀링, 수명·동시 수·화면 면적 제한을 갖는다. 적 전조, 플레이어, 바닥의 우선순위가 아군 VFX보다 높아야 한다. 마을 UI는 실제 모바일 터치 프롬프트를 사용하며 영상의 `[E]` 표기를 그대로 복사하지 않는다.

## 6. 구역→구역→보스: 기존 구조의 확장

현재 10구역 스트리밍은 존재하지만 최신 서버는 모두 측면 레인이며 끝에서 승리 처리한다. 원하는 구조에는 아래 데이터 계약을 **추가 제안**한다.

| 구역 필드 | 예시 | 담당 |
| --- | --- | --- |
| `roomKind` | village / traversal / combat / boss | 서버 진행·클리어·보상 계약 |
| `cameraMode` | Side25D / QuarterView | 서버가 구역 규칙으로 전달, 클라이언트가 표시 |
| `movementMode` | lane / plane | 서버 이동·충돌·클라이언트 예측이 동일하게 사용 |
| `sceneKey`, `nextZoneId` | 환경 씬 식별자, 다음 구역 | 로더 및 준비 신호. 보스 진입에 고정 0..9 가정 제거 필요 |
| `encounter`, `artProfile` | 전투 정의, 미술 설정 참조 | 게임 규칙과 미술 값을 분리 |

위 필드명이 최종 API 스키마는 아니다. 기존 map/state 필드를 우선 확장하고 중복 데이터 원천을 만들지 않는다. 예시 진행은 **측면 마을 → 측면 이동 → 쿼터 전투 → 측면 이동 → 쿼터 보스**다. 실제 구역 수·보상 설계는 기존 게임 진행 구조와 맞춘다.

전환 순서:

1. 현재 구역 활성 중 다음 환경을 준비한다. 현재 방식처럼 로드를 완료하고 환경 루트를 비활성으로 둔다. 아직 표시되지 않는 씬에서 AI·오디오·트리거가 실행되지 않는지도 확인한다.
2. 클라이언트의 `readyZone`를 기존 세션 흐름으로 전달한다. 서버는 클리어·입장 조건과 준비 상태가 모두 만족될 때만 다음 구역을 확정한다.
3. 짧은 페이드 동안 현재 구역 입력·전투 표현을 정리하고 서버가 확정한 구역으로 전환한다. 전환 중 입력의 폐기/보류 정책을 한 곳에서 처리한다.
4. 새 환경·카메라·접지·HUD가 같은 구역을 가리키는지 확인한 뒤 페이드를 연다. 기존 공유 전환 진행도를 사용한다.
5. 이전 구역을 해제한 다음 그다음 구역을 준비해 환경 씬 최대 2개를 유지한다. 현재 `Resources.UnloadUnusedAssets()` 시점과 씬 활성화 비용을 측정한다. 매 전투 프레임 호출로 옮기지 않는다.
6. 로드 실패·재접속·나가기·빠른 재입장에서는 단일 로더 소유권을 유지한다. 실패 안내 후 재시도나 안전한 복귀가 가능해야 하며, 존재하지 않는 준비 완료 신호를 보내지 않는다.

`allowSceneActivation=false`로 0.9에서 씬을 붙잡는 방식은 현재 코드와 다르다. 이 상태가 다른 비동기 씬 해제 큐도 막을 수 있으므로 근거 없이 바꾸지 않는다. [Unity 씬 활성화 문서][unity-activation].

보스 연결은 기존 별도 보스 세션으로 넘기는 방식과 같은 Mount 세션에 boss encounter를 추가하는 방식 중 **한 방식으로 계약을 고정**한다. 새 보스 규칙을 복사하기보다 기존 보스 로직 재사용을 우선 검토한다. 세션 ID·입장 티켓·클리어 결과·중복 정산 처리와 실패 복귀까지 검증한 뒤 연결한다. 단지 카메라가 쿼터로 돌아간 것을 보스 구현 완료로 보지 않는다.

좌표는 기존 **100 core units = 1m**, laneY를 뺀 깊이, 공유 높이 샘플을 유지한다. `planar=false`, `RpgSession.PlanarMovement`, `NativeBattle`의 일반 구역 측면 강제를 함께 고쳐야 한다. Unity Rigidbody와 서버가 각자 이동 권위를 갖게 하지 않는다.

## 7. 실제 수정 위치

표의 Unity 경로는 실제 통합 프로젝트 기준이다. 폴더 없이 파일명만 쓴 Runtime 스크립트는 `Assets/Island/Runtime/` 아래를 뜻한다. 원격에서는 감사 문서의 고정 snapshot 링크로 대응 파일을 확인한다. 날짜별 snapshot은 적용 증거이므로 기존 역사 기록을 수정하는 방식으로 개발하지 않는다.

| 작업 | 주요 대상 | 지켜야 할 계약 |
| --- | --- | --- |
| 구도·시점 | `Assets/Island/Runtime/Battle3DView.cs`, `BattleCameraController.cs`, `NativeBattle.cs`, `ViewPresentationCoordinator.cs`, `IslandBattleHud.cs` | Mount 프리셋 override·서버 시점 강제·뷰포트를 함께 확인. 기존 전환 소유자 유지. |
| 풀 군락·LOD | `Assets/Island/MapMigration/Runtime/MapReviewGrass.cs`, `Assets/Island/MapMigration/Shaders/ZoneGrass.shader`, 신규 배치 데이터/에디터 도구 | 셀 컬링·호출당 인스턴스 제한·최대 변위 bounds·공유 재질. |
| 지면·원경 | `Assets/Island/MapMigration/Shaders/ZoneGround.shader`, `MountZoneEnvironment.cs`, 기존 구역 씬·마테리얼·cubemap | 지형 높이·충돌 보존, 전경 디더 깊이 패스 일치. 실제 자산 경로는 프로젝트에서 확인. |

| 이동·보스 진행 | `src/lib/rpg-mount-sunday-engine.ts`, `src/app/api/rpg/mount-sunday/route.ts`, 관련 service, `RpgSession.cs`, `MountRoute.cs`, `NativeBattle.cs` | 권위와 예측의 같은 규칙, 보상·티켓 중복 방지, 구역 준비 확인. |
| 소품·재질 | 기존 환경 리소스, `BattleDioramaLook.cs`, 신규 prefab·material | 변경 전 캡처, 기존 캐릭터·폰트·수동 자산 보존, 생성 소품은 검토본으로 분리. |

파일별 작업 묶음을 별도 커밋으로 남긴다: (1) 구도/대표 장면 (2) 풀/팔레트 (3) 구역 계약/보스 연결 (4) 실기 최적화. 한 커밋에서 이동 판정과 전체 아트 교체를 섞지 않는다.

## 8. 검증과 배포 게이트

### 미술·기능

- 같은 해상도·카메라·시드·시간의 전후 캡처: 사이드 마을, 이동 중 길 경계, 쿼터 전투, 보스 최대 VFX, 언덕 전경 가림, 구역 입구.
- 폰 크기로 축소해 플레이어·적·길·전조를 즉시 식별. 잔디 뿌리 미끄러짐, LOD 팝인, 배경 카드 끝, NPC 프롬프트 가림이 없어야 한다.
- 기존 6m/s 이동과 살아 있는 슬라임 몸통 차단·죽은 슬라임 통행을 보존. 측면/평면 입력 규칙과 카메라 전환을 모두 확인.
- 로딩 지연·실패·나가기/재입장, 느린 응답·중복 응답에서 구역과 환경이 일치. 환경 씬 최대 2, 퇴장 후 환경·풀 자원 정리, 오류·Missing Script 0.
- 명령은 해당 구현 브랜치 `package.json`을 확인한 뒤 `npm run check:rpg`, `npm run test:rpg:mount`, `npm run test:rpg:unity-boss` 실행. 규칙 변경 때 관련 회귀와 일반 입력 완주를 추가한다. 미술만 수정하면 해당 범위 P0·렌더 확인부터 한다.

### Android — 아래 숫자는 새 제안 목표이며 달성 결과가 아님

| 조건 | 측정·수용 기준 |
| --- | --- |
| 목표 기기 | 실제 저사양 기준 기기 1대와 중간급 1대 선정. 모델·OS·GPU·API·해상도·렌더스케일·품질·빌드 SHA 기록. |
| 지속 부하 | 고정 시드·같은 입력으로 10구역 및 보스, 최소 20분 반복. 워밍업, 일반 전투, 전환 구간을 따로 기록. |
| 30fps 기본 단계 | 워밍업 후 전투 p95 프레임 시간 33.3ms 이내를 초기 목표로 설정. 실패 시 GPU/CPU 병목을 먼저 구분. |
| 60fps 단계 | 여유 있는 기기에서 p95 16.7ms 이내를 목표. 평균 FPS만으로 통과하지 않음. |
| 지연 | p99·최악 프레임·50/100ms 초과 횟수·로드 시작→준비→활성화→페이드 해제 시간을 각각 기록. 페이드 길이와 프레임 스파이크를 혼동하지 않음. |
| 메모리·발열 | PSS/Unity allocated·reserved/GC 지표를 각각 추적. 반복 진입 후 지속 증가가 없는지, 장시간 FPS·배터리·온도 변화를 기록. 기기별 예산 확정 전에는 메모리 PASS를 임의 선언하지 않음. |
| 품질 축소 순서 | 먼 풀 밀도·거리 → 장식/꽃 → 파티클 화면 면적 → 그림자 거리·해상도 → 렌더스케일. 플레이어·적·전조 판독성은 유지. |

Development build로 CPU/GPU·할당 원인을 찾고, 배포용 설정 APK로 지속 성능을 다시 확인한다. 실제 목표 플랫폼에서 프로파일링해야 한다는 근거는 [Unity 성능 측정 문서][unity-profile]를 따른다. 기존 BlueStacks 값은 비교 보조 자료다.

### 출시 경로

1. 기능 브랜치와 최신 실제 프로젝트 상태를 통합하고 관련 회귀·화면·실기 검증 기록을 남긴다.
2. 호환 서버와 APK의 API/콘텐츠 버전을 맞춘다. 로컬 `adb reverse` 의존을 제거한 설치·접속 검사와 필요한 서버 배포를 수행한다.
3. 새 APK 및 정확히 대응하는 소스 패치/전체 프로젝트 구분, SHA-256, 테스트 증거를 릴리스에 올린다. 서버 배포만으로 Unity 자산이 갱신된다고 안내하지 않는다.
4. 미술 최종 승인은 사용자의 두 대표 장면 비교로 받는다. 자동 검사 통과를 미술 승인으로 대체하지 않는다.

현재 요청의 산출물은 이 계획과 상태 진단 문서다. 런타임 코드·서버 배포·APK 갱신은 이 문서 PR의 변경 범위에 포함하지 않는다.
